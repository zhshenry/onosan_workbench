# Windows cloud acceptance pilot

This simplification candidate runs complete Windows baseline checks and installed-app acceptance for PRs targeting `main`, pushes to `main`, and manual dispatch. It does not merge main, publish a release, register a self-hosted runner or involve a personal computer. It uses a standard `windows-2022` GitHub-hosted runner with read-only repository permissions, concurrency cancellation and a 25-minute job timeout. Windows-only acceptance is conditional on real file-symlink and parent-directory-junction rejection tests passing at this exact candidate commit; otherwise retain the smallest necessary Linux fallback. Those runner results are not yet established by this document. No Actions cache is uploaded.

## Trigger and trust boundaries

- `pull_request` to `main`: `opened`, `reopened`, and `synchronize` (new head commits). Draft PRs are included. PR title/body edits, reviews, labels and ready-for-review transitions do not rerun the same commit. Retargeting an existing PR to main alone does not trigger a run; push a new head commit or reopen it before acceptance.
- `push` to `main`: check the exact new main commit, including a merge performed separately by an authorized maintainer. Feature/pilot branch pushes have no second push run; their open PR supplies the check. A feature branch without a PR does not trigger this workflow.
- `workflow_dispatch`: manual checks use the selected ref. GitHub requires the workflow on the default branch for the manual entry point. Historical PR and main-push routes succeeded as recorded below; this candidate must be checked at its own commit. Dispatch remains configured; this document records no new dispatch test. Do not merge or dispatch merely on the authority of this documentation.
- No path filters: all PRs to main and main pushes are checked, including documentation-only updates. This also covers build configuration, assets and tests without maintaining an incomplete source-path allowlist. The candidate has one Windows job per qualifying event, subject to the fallback condition above. A newer run cancels an older run for the same PR or same event/ref; manual, PR and main-push routes have separate concurrency groups.
- Same-repository and fork PRs use the ordinary `pull_request` event, never `pull_request_target`. They test GitHub's proposed merge with main using default checkout behavior. Evidence records the tested merge SHA plus separate head/base SHAs and event. Merge conflicts prevent GitHub from starting PR checks and must be resolved before acceptance.
- The workflow requests only `contents: read`; checkout does not persist credentials. No repository secrets are referenced or injected into test/package/app processes. The workflow cannot publish a release, comment on a PR or write repository contents. Fork/Dependabot runs remain subject to GitHub's existing maintainer-approval policy; this change does not bypass approval or alter Actions/security settings. Do not add privileged triggers, secrets, self-hosted runners or downstream execution of PR artifacts.

Event behavior and fork restrictions follow [GitHub's event documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). Source-contract regression tests check this configuration, but do not simulate event delivery. The successful [PR run 37124795071](https://github.com/zhshenry/onosan_workbench/actions/runs/37124795071) tested head `58162e7357533799b21fc7a72e378eb5c57909e8`. The successful [main push run 37133922363](https://github.com/zhshenry/onosan_workbench/actions/runs/37133922363) tested merged main `36f9428b59e97c74d405e396c0cdab8e4c6424cf` (attempt 1). These run statuses were checked on 2026-10-08; historical screenshots were not re-reviewed. These are historical two-platform results, not validation of this Windows-only candidate. This is CI evidence, not deployment of the proposed [OnO issue workflow](ONO-ISSUE-WORKFLOW.md).

## Evidence and spending boundaries

A single evidence directory may contain only the [guard’s fixed allowlist](../tooling/pilot-artifacts.mjs): six base PNG names, the fixed year-dropdown/AI-card/topbar/floating-group PNGs, four updater-status PNGs, and three JSON/Markdown reports. A guard rejects unexpected names, directories, symlinks, files without the eight-byte PNG signature, malformed JSON or a combined size over 19,000,000 bytes, leaving headroom within the approved 20,000,000-byte ZIP target. The PNG guard does not perform a full image decode; screenshots must also be visually reviewed.

The **entire workflow run**, including any necessary Linux fallback, has exactly one artifact upload, in the Windows job; no second upload is allowed. That step runs only after the guard passes and retains evidence for 3 days. The artifact is named by run ID without attempt number and uses `overwrite: true`, so a rerun with safe new evidence replaces that run's existing evidence rather than accumulating another artifact. If a rerun fails before producing safe evidence, the prior artifact can remain; it is not evidence of the new attempt. Reports include `runAttempt`, and acceptance must match the latest successful attempt plus tested/head/base SHAs. Workflow regression tests enforce this single-upload configuration and the absence of the two retired manual pilot YAML entrypoints. Adding another upload/job requires revisiting the aggregate run budget, not assigning another 20 MB allowance. Separate runs have separate budgets and still count toward the account-wide storage allowance.

No installers, portable ZIPs, videos, traces, databases or real user data are uploaded. Large installer/Office native runtime files stay on the disposable runner; the full portable-release repack step is intentionally omitted.

Standard hosted runner compute is free for public repositories according to [GitHub billing documentation](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Account-wide artifact allowance and enabled-Action settings still need to permit the run/upload; this workflow does not change billing, storage quotas or security settings. A quota/admission error is a blocker, not permission to enable paid capacity.

## Limits

This is silent NSIS install and same-version persistence coverage. It does not assess the native wizard, UAC, SmartScreen, publisher trust/code signing, real automatic updates, cross-version upgrades, Office conversion, AI provider calls, login-at-start or another application's actual shared database. `WORKBENCH_TEST_DATA_DIR` isolates both `OnoWorkbench` and `To-Do-List`; it intentionally disables automatic updates and launch-at-login registration.

Production release commands and version/tag procedures remain in [RELEASE.md](RELEASE.md). CI does not increment versions, create tags or release anything. A green check does not authorize a merge or release. The recorded pilot used product version `0.1.0`; same-version relaunch coverage is not true upgrade acceptance.

## Issue #37 local published-work association coverage

The installed-app pilot adds twelve named acceptance checks for the approved [Issue #37 v1 scope](https://github.com/zhshenry/onosan_workbench/issues/37#issuecomment-6140325358). Two synthetic blogs are created and saved through the normal blog editor, with exact identity, creation/update timestamps, title, body and platform read back through the real `copy:list` API and the isolated `userData/copy-drafts.json` file. Earlier pilots' blogs are frozen before creation; exactly two new UI-created IDs belong to this pilot. Every disk checkpoint requires all earlier records and their relative order to remain unchanged, rejects missing/extra/duplicate IDs, and preserves the complete final store for the real restart comparison. The reference-picker pilot runs first and its reference snapshots and blogs remain intact. The preparation heading/instructions and original title/body clipboard actions are checked without opening any platform page.

The association checks cover unlinked, format-error, pending-confirmation and manually linked states; complete local title, canonical URL, remote ID, source and confirmation time; changed-input invalidation; keyboard check/cancel/selection; cancelled replacement; two-stage removal cancellation; and blog switches without moving transient state or writing the other blog. Successful confirmation, replacement and removal are performed through normal UI controls. Every association-only write must preserve all original blog fields, including `updatedAt`; cancellation and invalid input must leave the complete store and disk JSON unchanged. Navigation and a normal renderer reload are followed by an actual full application quit and relaunch of the same installed executable, reading back both the retained association and the absent removed association.

Three explicitly separate fixture-only checks inject bounded failure/delay into the existing `copy:markXhsPublished` and `copy:clearXhsPublished` handlers for the actual main frame only. A delayed native double-click must invoke one handler and keep its captured blog target across selection changes or page navigation. Failures must leave real disk data unchanged and show a local error for retry. The fixture retains the exact original handlers, limits a pending delay to 10 seconds, rejects unknown handler drift, and restores the originals in `finally`; the final successful persistence and full restart checks run with the fixture removed. The fixture does not replace reads, mutate the renderer DOM, call write APIs directly, or fake a storage/restart result.

All four association states are measured at actual 1280×820 and minimum 1024×680 native content sizes in the three existing themes, with normal and reduced motion. Complete long text and errors, normal scrolling, keyboard controls and real pointer hit targets are checked. Four fixed unmodified native app screenshots (`publish-association-unlinked.png`, `publish-association-pending.png`, `publish-association-linked.png`, `publish-association-error.png`) join the existing aggregate allowlist. Together with the retained reference-picker and update-status evidence, there are now 53 success PNGs / 56 success files, or 57 files including a failure screenshot, under the unchanged 19,000,000-byte raw / 20,000,000-byte ZIP ceiling, one artifact upload and 3-day retention. No PNG is committed or backed up, and no JSON database is uploaded separately.

These are acceptance assertions to be executed by the existing Windows Actions route for the exact candidate commit. Local unit/source-contract passes do not establish native acceptance or visual review. The cloud headless environment's denied socket operation is not bypassed; native install, interaction, screenshot and restart results remain unverified until the real Windows run finishes. No actual platform publication, update, deletion, scraping, account sync or online work verification is covered or attempted.
