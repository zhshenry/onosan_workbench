# TRAE CN 授权复核 · 2026-11-15

用户反馈浏览器显示「登录失败／网络错误」，并询问是否对应 Windows 中的 TRAE CN 应用。本机快捷方式指向 `Programs/Trae CN/Trae CN.exe`，官方安装包 `product.json` 的名称为 TRAE CN，应用版本 `3.4.17`，底层编辑器版本 `1.107.1`，协议为 `trae-cn`。版本身份已核对；截图本身不足以证明网络故障的具体原因。

对照本机官方安装包的公开程序配置和登录实现，发现工作台授权用了 SOLO 的客户端标识与 `auth_from=solo`，回调仍要求旧版直接令牌，缺少当前的授权码、PKCE 与续期设备签名。未读取官方应用账号数据库、令牌或私钥。

## 修正

- 使用 TRAE IDE 稳定版客户端 `ono9krqynydwx5`、`auth_from=trae` 与当前版本参数；设备元数据仅读 TRAE CN 目录。
- 登录链接包含 S256 挑战，校验码只在本机用于交换。回调只监听 127.0.0.1 随机端口的固定 `/authorize` 路径，接收一次有效的 `authCodeInfo.AuthCode`，并核对每次独立生成的 `loginTraceID`；只允许官方网页来源及其预检，不允许任意跨域来源。
- 从 `api.trae.cn/trae/api/v3/oauth/ExchangeToken` 换取令牌，再查询真实用户身份；不信任浏览器回传的账号名称或 ID。
- 为本连接生成 P-256 密钥，公钥用于设备绑定，私钥只在现有加密凭据中保存。续期使用同一密钥签名，旧连接缺少密钥时要求重新授权，不尝试绕过校验。

## 验证

新增回归先在旧实现复现：授权来源为 SOLO；浏览器预检返回 404；旧连接续期仍调用旧接口。

用户随后确认 TRAE CN 本身能正常登录，但工作台新链接仍显示失败。继续核查官方授权页当前公开脚本 [authorization/page.f3f2728ac7.js](https://lf-cdn.trae.com.cn/obj/trae-com-cn/trae_website_prod_cn/static/js/async/authorization/page.f3f2728ac7.js)，发现其在发起登录前要求回调严格匹配 `^http://127\.0\.0\.1:(\d+)/authorize$`。先前加在路径中的随机段会触发 `invalidUrl`，网页直接显示失败；这是首轮修正遗漏的网页兼容性问题，不能归因于用户网络。

修正回调为官方固定路径，将本轮随机校验移入官方实际回传的 `loginTraceID`（网页从外层 `login_trace_id` 生成该字段），并保留 PKCE。新增断言先复现路径不匹配，随后验证固定路径及缺少／错误 trace 被拒绝、正确 trace 可继续一次性回调。浏览器实机探测打开超时，未作为验证通过的证据。

修正后的回归使用虚构授权码与平台响应，通过真实本机 HTTP 端口验证官方来源预检、一次性回调、取消、PKCE 对应关系、当前交换入口、服务器身份确认、续期签名和密钥保护。密钥经加密落盘、令牌轮换与服务重启后仍保留；页面状态和网络请求不包含私钥。原三家签到与 IPC/UI 回归一并检查。

## 真实账号签到状态排查

用户随后提供的工作台截图已显示 TRAE CN 账号连接成功，但签到显示“暂无可领取活动”，明细为账号或设备校验失败。2026-11-15 使用工作台自己保存的连接进行两次只读状态查询：原请求体 `{}` 与官方请求体 `{ req_source: 1 }` 均返回 HTTP 200、`code: 0`、`enable: true`、`checked_in: false`、`credits: 100`。因此此次查询证明当天尚未签到且活动可用，不能把此前的校验失败解释为没有活动，也不能据此断言领取接口已经恢复。

核对本机 TRAE CN 3.4.17 公开程序 `resources/app/out/main.js`：`_requestCheckinCredits` 对状态和领取接口均传入 `{ req_source: 1 }`（SOLO 为 2）；`_applyUgDeviceHeaders` 使用设备服务的 `guaranteedDeviceId`。工作台此前请求体为空，且误用机器标识作为签到设备 ID。

用户明确同意使用当天签到机会后，使用同一工作台登录连接对照真实领取：机器标识加正确来源参数仍返回 `code: 9074`、消息“当前参与用户太多，请稍后再试”，随后状态仍为未签到。仅改为本机官方客户端初始化的已注册设备 ID，领取返回 HTTP 200、`code: 0`，随后状态返回 `checked_in: true`、`did_checked_in: true`。这组对照确认了机器标识与签到设备标识混用的问题；不能把 9074 单独解释为账号无效或一定是平台繁忙。领取前平台报告可领取 100 积分；领取响应本身不含奖励数值，不编造额外到账明细。

修正为：来源参数补齐；签到状态和领取请求单独读取 `Trae CN/logs` 最近一次官方启动日志头部的设备初始化成功标记，最多读取 256 KiB。不能识别时停止请求并提示先打开官方应用，不退回机器标识或旧启动记录。已保存的 OAuth 设备绑定及续期密钥保持原值，不要求重新授权，不扫描或解密其他应用的登录凭据，也不生成或轮换设备身份。该读取依赖当前官方初始化标记，客户端版本变化导致标记不可识别时会明确失败。
