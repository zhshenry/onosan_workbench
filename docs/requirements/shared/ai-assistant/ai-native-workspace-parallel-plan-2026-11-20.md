# OnoSan 与 CMO 的 AI 原生工作区方案与并行实施计划

2026-11-20 · 方案稿 · 第一阶段待实施

从第一阶段起，两仓同时改真实业务。OnoSan 用总管看板验证“人移卡、Bot 改样式、人接着编辑”，CMO 用办公助理验证“人选事项、Bot 准备待办、人确认后改期”。两条线使用同一套操作和回执规则，各自可以开发、自测和演示。CMO 仓库有可单独使用的[第一阶段开工单](../../../../../cmo_workbench/docs/requirements/shared/ai-assistant/ai-native-workspace-cmo-kickoff-2026-11-20.md)。

## 一、产品目标

每个 Bot 有一个主要工作区、一条持续主对话和一组获准使用的工具。用户能直接在工作区操作，也能把工作交给 Bot。接手的一方可以定位原对象、读到它的最新状态，知道目标中哪一步已经做完。需要其他专业能力时，当前 Bot 可以把明确的工作和资源引用交给另一位 Bot。

| 组成 | 产品约定 |
| --- | --- |
| 本地工作区 | 有稳定 ID，绑定业务对象、可用面板、工具和 Skill。一个工作区可同时包含浏览器、文件等面板。原生业务数据仍由所属模块保存。 |
| 总管与领域 Bot | 默认负责人是总管，已有名字和身份沿用。用户也可以直接找领域 Bot。总管能操作自己的总台，跨域工作交给有能力的负责人，并从业务回执汇总结果。 |
| 预制与自定义 | 两者共用工作区实例和执行机制。预制模板由各产品随附，自定义实例由用户选面板、绑定资源、选择工具及 Skill。同一模板可以产生两个范围独立的实例。 |
| 工具与 Skill | 工具执行可验证的动作，Skill 说明如何组合动作完成工作。Host 和业务适配器在执行时核对工作区、原用户授权、对象及本次用途。名录根据实际绑定展示能力。 |
| 运行与互通 | 每个产品内由现有本地 Host 管理 Bot。询问、通知、委派、人工确认和真实结果沿用已有协议。窗口不可用时，依赖该窗口的操作等待资源。电脑恢复后先核对任务和在途写入。 |

首期按**各产品内 Bot 互通**设计。两仓共享行为约定、测试输入和已有事项库规则。聊天、办公资料、模型配置、凭据、浏览器登录范围和卡片目录分别由所属产品管理。既有跨应用共享待办以[事项库约定](../../../../modules/todo/SYNC.md)为准。

## 二、GUI 和 LUI 共用什么

一次业务操作的路径是 **定位对象 → 读取当前状态 → 校验和执行 → 取得结果 → 更新工作区与对话**。GUI 提交用户明确保存的操作，LUI 提交解释后的同一种操作。各模块复用现有服务、校验和确认入口。首次只在两个试点实现下列行为，等第二个模块接入后再提取重复代码。

| 环节 | 两仓共同规则 |
| --- | --- |
| 指向 | 发送时固定工作区、目标对象及当时版本。能唯一定位的“刚挪的那张”“这条事项”可直接使用，多个候选让用户选一次。切标签、切 Bot 或切账号后仍按原目标核验。 |
| 状态与进度 | 模块返回正式状态和相关的已提交变化。人工操作可以没有 Bot 任务。只有明确目标中的动作才推进任务步骤。聊天、选中态、未保存草稿和业务已提交各有含义。 |
| 执行 | 写入携带操作 ID、操作者和目标版本，沿用领域确认规则。重复投递同一操作返回原回执。版本变化先重读，目标已满足即可核实交付，有冲突则保留当前值供重新选择。 |
| 回执与接续 | 写入者返回本次实际影响的对象 ID、最终版本或真实业务凭据。任务记录关联该回执，GUI 按它刷新，Bot 下一轮按对象 ID 回读。跨库或外部提交中断时保留“待核对”，先查原对象或业务记录。 |
| 委派 | 发送方给出目标、允许共享的引用和完成条件，接收方在自己的工作区复核。用户可从发起会话处理同一张确认卡。“已接收”“等用户确认”“业务已完成”分别显示。 |

原生面板可让 GUI 和 LUI 调同一个业务服务。第三方网页靠同一授权会话、标签页和最新观察接手，已适配站点再增加表单字段和业务回执。文件靠授权目录、对象位置和文件版本。终端靠受限命令、进程状态与产物，开放自由 Shell 的前提是实际的进程、文件和网络隔离。

## 四、并行路线

| 阶段 | OnoSan 同期交付 | CMO 同期交付 | 联合验收 |
| --- | --- | --- | --- |
| **一 · 跑通第一条双向操作** | 修正待办回执。总管能读取看板，并对用户刚保存移动的卡片修改样式。 | 为现有待办回执补同组回归。办公助理能将选中事项转为原对话中的待办建议，并从原事项继续。 | 两仓均有“人 → Bot → 人”的隔离实窗演示。相同交错写入样例中，两个数据库连接各自只认领自己的操作。 |
| **二 · 补齐预制工作区的业务动作** | 看板补齐添加、移动、调尺寸、改样式、移除。以日程、稿件为下一批，接入原负责人的读写、确认和交付。 | 总台接入本产品的卡片目录与相同布局动作。办公补齐标为已处理、来源回查和关联待办。日程沿用企业来源规则。 | 两仓分别维护完整的预制能力清单。看板移除卡片只改变布局。跨 Bot 追问、改期和确认都落在原业务对象，待办库互操作通过。 |
| **三 · 支持浏览器接手并扩展领域覆盖** | 网页或自媒体 Bot 接手用户已筛选的页面，核对当前标签、条件和分页后继续采集，结果带来源。按能力清单补其余预制工作区。 | 权限 Bot 从纯人工填写到一半的 PIC 表单建立进度。PBI 按实际授权标签开展只读任务，写操作按适配能力开放。 | 用户介入后重新观察。标签关闭、换账号、页面失效或回执未知时停在正确状态。正式提交有对应业务凭据。 |
| **四 · 开放自定义 Bot** | 用浏览器与指定目录组合一个资料整理 Bot。沿用现有名录、主对话、委派、任务和交付件。 | 用企业允许的面板、连接与 Skill 配出工作区。按账号和产品策略核对资源范围。 | 各产品能创建两个同模板、不同资源范围的实例。总管可分别委派，重启后身份和成果可回查，跨范围调用在执行端被拒绝。随后开放通过隔离验收的终端能力。 |

共同功能以同一组业务样例核对，产品特有功能各自在本仓接入。第一阶段开工清单已给出共同口径，开发者可以立即并行工作。若一仓先完成，可先跑本仓回归、推进独立任务。涉及共用事项库格式或跨版本协议的改动，由两端兼容性用例共同决定交付顺序。

两条线有三个对齐时点。**开工时**，各仓以本仓用例和真实业务入口为起点。**首条流程可运行时**，双方交换一份样例，列出输入对象、操作者、操作 ID、原版本、实际结果及凭据，核对两端对“已保存”“待确认”“待核对”的解释。共用行为有变化时一起更新样例，各仓独立管理自己的 Host 协议版本。**阶段结束时**，用两仓当前版本跑同一个临时库和两条实窗流程，分别记录结果。

## 五、第一阶段开工清单

### 两仓开工时同时做

1. 各自记录工作树版本、隔离数据目录和初始测试结果。使用合成资料，保留一份旧看板及一个空看板样本、一组有明确来源的办公事项样本，并约定两连接交错写入的次序。日期用例固定在周一的本地测试时钟，断言“本周五”和“本周四”对应的实际日期。
2. 各自在本仓从预制名单和真实页面登记业务动作。OnoSan 覆盖总台、日程、自媒体、游戏、网页、AI 测试、命理和阅读。CMO 覆盖总台、日程、办公、权限、交付件、PBI 和 DTS。盘点与试点开发同期进行。
3. 每项记录“工作区、用户动作、GUI 入口、Bot 入口、执行模块与对象 ID、授权或人工环节、成功凭据、尚缺环节”。现有服务可复用、缺工具入口、缺权威状态、需要人接管要能分别辨认。CMO 的交付件及 DTS 按已接入的数据源登记。

### OnoSan 开工单

| 次序 | 要交付的改动 | 本仓验收 |
| --- | --- | --- |
| 1 | 在 `Store.applyPlan` 的写事务里记录实际创建、更新的 ID，在事务末尾返回最终对象。Bot 执行器直接采用返回值，保留已选择的操作序号及数量。 | Bot 提交后、读回执前由第二个连接建一条事项。库里有两条，回执只含 Bot 的一条。同对象连改两次返回最终值，事务失败没有成功回执。 |
| 2 | 为总台提供读布局和提交布局的后端入口，布局及版本保存在本产品的数据目录。首次由 GUI 将旧布局按原解析规则导入。区分“尚未导入”和“已保存空看板”，导入成功后才启用新来源。GUI 的“完成”提交，“取消”舍弃本次草稿。 | 重开、重复导入都保留原卡序、尺寸、样式及留白。导入失败保留原值供重试。Host 早于首次 GUI 连接时，等待可核对的正式布局。 |
| 3 | 先向总管开放“读看板、改样式”。用户保存移动后记录目标卡片和布局版本，样式修改只提交目标卡允许的样式，GUI 和 LUI 走相同布局校验。 | 人将 AI 额度卡移到右上并保存，说“把刚挪的那张改成圆环”。位置保持、样式变化，人可继续改尺寸。未保存拖动、过期布局、卡片已移除、一次移动多个候选均有可解释的结果。 |

实现入口为[看板组件](../../../../src/views/HomeView.tsx)、[共享布局函数](../../../../shared/dashboard-layout.ts)、[待办 Store](../../../../modules/todo/store.ts) 与 [Bot Runtime](../../../../electron/bot-runtime.ts)。基线测试从[看板](../../../../tests/home-dashboard.test.ts)、[双连接待办](../../../../tests/todo-shared.test.ts)和[待办补充](../../../../tests/bot-todo-followup.test.ts)扩展。

### CMO 开工单

| 次序 | 要交付的改动 | 本仓验收 |
| --- | --- | --- |
| 1 | 把相同交错写入样例补入回归。用现有事务回执作基线，同时开始打通办公动作。 | 两个连接都能读到两条事项，Bot 回执只含本次对象及其最终版本。 |
| 2 | 用户从办公工作区说“把这条排到周五”时，发送时绑定办公事项 ID 和来源 ID。执行端按当前账号重新解析，生成精确日期。按钮与受限 Bot 工具进入同一准备建议的业务逻辑，沿用办公主对话和原确认卡。 | 两条同名事项中总是选中发送时那一条。先点按钮再补日期，更新同一待确认建议并使旧版本失效。切账号后原引用失效。确认前待办库零写入。 |
| 3 | 确认后按实际待办 ID 建立与办公事项的关联，从该 ID 读当前日期。已创建后的新改期按已有待办修改规则处理。 | 重复确认只写一次。用户随后在日历手动改到周四，回到办公助理询问时读到周四，且可定位原来源。 |

CMO 可以直接按[本仓开工单](../../../../../cmo_workbench/docs/requirements/shared/ai-assistant/ai-native-workspace-cmo-kickoff-2026-11-20.md)实施。办公事项 ID、来源消息 ID、业务待办 ID、Bot 工作任务 ID 各自保留用途。已有建议只能由原持有者按权限更新，实际写入仍需原确认。

### 第一阶段联合演示

| 验收场景 | 通过条件 |
| --- | --- |
| 双向接续 | 在各自业务界面先手工完成 A1，Bot 直接完成 A2。再手工修改一次，Bot 回读最后保存的业务值。两端均能指出实际对象。 |
| 两仓共享数据 | 两个产品的 Store 打开同一份临时事项库，各写一条。核对可见性及各自回执，再对同一事项的旧版本写入验证冲突。 |
| 重试与中断 | 相同操作 ID 重发只返回已有结果。重启后已保存布局、关联的待办、待确认状态可以定位。对已发出但结果未知的写入先核对业务数据。 |
| 权限和上下文 | 无关 Bot 无法修改总管看板或其他账号的办公事项。切页、切 Bot 或协作转发均按原目标和授权重新核验。 |
| 实窗和证据 | 每仓留一条隔离 Electron 操作记录，附工作树版本、所用数据、对象 ID、版本或回执和失败情况。共享用例、产品用例分别记结果。模拟服务与真实业务联调注明环境。 |

## 六、后续接入时的判据

- **预制工作区覆盖。** 每个已开放的可委托业务动作都有 GUI/LUI 入口、权威数据来源、授权及可重复的验收。目录中同时标出人工环节和待接入系统。卡片从目录创建，实例按产品当前规则寻址。确有同卡型多实例需求时再分离卡型和实例 ID。
- **网页接手。** 通用网页在当前获准标签重新读取筛选和结果。PIC 等已知站点从页面可验证字段恢复草稿，保留正确字段，提交前复核目标、参数和确认。网页上的成功提示需要与本次对象对应，申请已提交和审批生效分别核对。
- **自定义配置。** 模板 ID 标记来源，每个工作区实例有独立 ID，分别保存面板、资源绑定和允许的工具及 Skill。将当前依赖固定预制名单的寻址和唯一约束迁移到实例，保留旧 Bot 身份、聊天、任务和用户改名。用户可从模板或空白工作区创建实例，保存后即能在名录发现和委派。初版组合浏览器和文件，终端先接有边界的项目命令。
- **两仓交付。** 每阶段由两个产品各交业务结果、测试证据及剩余缺口，共用契约在同一轮评审。界面与领域能力可独立演进，只有两边都满足该阶段联合验收后，才把双仓里程碑记为完成。

现有 Host、持续主对话、分入口草稿、任务调度与协作消息的细节以[通用 Bot 架构](bot-workbench-architecture.md)及[协作实施记录](bot-collaboration-implementation-2026-11-17.md)为依据。本文负责工作区动作、人机接续和双仓实施顺序。
