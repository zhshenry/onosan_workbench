# OnO Bot 工作台接入方案

日期：2026-11-13。更新：2026-11-15。状态：接入方案，尚未实施。通用架构、数据、协作、双模式交互和验收以[通用个人 Bot 工作台架构方案](bot-workbench-architecture.md)为准；本文记录 OnO 的业务映射、视觉选择及迁移要求，并给出未来接入 CMO 的对应位置。

当前已运行的行为仍以 [DESIGN.md](../../../../DESIGN.md)、[UX-CONTRACT.md](../../../../UX-CONTRACT.md) 和既有 [spec.md](spec.md) 为准。新行为随实现更新正式规范。

## 1 OnO 产品范围

OnO 接入通用 Bot Host 和 Pi 执行层，使用自己的模型配置、凭据、数据目录和业务工具；无需云端电脑。左侧工作台目录改为 Bot 联系人，现有业务页面进入各 Bot 的工作区。

| 项目 | OnO 接入要求 |
| --- | --- |
| 首页 | 后续重构为总台，承载总 Bot 主入口及跨工作台概况；完整首页单独设计 |
| 待办与日程 | 独立工作台及领域 Bot，保留既有共享库和上游同步约束 |
| 设置 | 保留人工设置弹窗，不创建设置 Bot、上下文或操作工具 |
| 助手 | 并排／浮动两模式，首次选择、记住上次、随时切换 |
| 后台运行 | 先以 Electron 托盘常驻，后续支持独立本地 Host；设备休眠或关机期间不能执行 |
| 业务页面 | 保留实际编辑、发布、项目、测试、浏览器和小工具页面 |
| 外围能力 | 既有灵动岛、通知和快捷入口接入新身份及任务来源，保留原有语义 |

设置仍可人工配置供应商、模型和密钥。显示模式只管理界面，Bot 资料和记忆从 Bot 自身入口管理。

## 2 Bot 和工作区映射

| 业务标签 | Bot 名字示例 | 负责的页面和资源 |
| --- | --- | --- |
| 总 Bot · 总台 | Ono | 跨领域请求、任务概况、待判断事项、Bot 名录 |
| 待办与日程 | 小历 | 日历、待办与日程资源，已有共享数据及同步 |
| 自媒体 | 小墨 | 博客编辑、图文发布、我的小红书；草稿及实际页面 |
| 游戏 | 游伴 | 游戏项目、运行、测试、问题和产物 |
| 网页与网站 | 小舟 | 浏览器、Hush-Hour、个人网站；各项目分别关联 |
| AI 测试 | 小测 | 对比测试、测试任务、运行记录 |
| 小工具 | 组织方式待定 | 命理、阅读和签到；是否增加领域 Bot 另行确定 |
| 设置 | 无 Bot | 人工配置 |

名字可改，业务标签保留；内部使用稳定 ID。原子目录保留为工作区模块，同类项目作为独立对象，不因改造自动合并或新增一级入口。

命理、阅读是否独立尚未确定，每日签到先保留现有功能与入口；导航重组不自动扩展账号操作能力。浏览器按实际任务、站点和标签授权，可作为获准 Bot 的执行能力。

## 3 OnO 双模式界面

沿用此前已选定的并排和浮动交互，按 [2026-11-15 外观优化方案](../../../design/appearance-system-proposal-2026-11-15.md)修订高保真。两种模式共享同一 Bot、主对话、任务、草稿、焦点和回复目标；收起后都保留胶囊，再打开时恢复原模式。

图稿统一以「悬浮导航 + 强玻璃 + 窗影·午后」打样。最新并排 v2 的布局与空间比例已获用户确认，作为后续实现的视觉依据；浮动两图保留为上一轮交互参考，身份入口与顶部布局同样遵循下方更新规则。设计确认不表示正式应用已实施；新安装和升级默认值仍按外观方案处理。

确认记录（2026-11-15）：用户针对并排 v2 回复「没问题」。确认范围为移除独立 Bot 身份行、对话与工作区上移后的空间比例，以及 Bot 信息、模式、任务和业务资料的入口归属。Bot 名片展开、资料编辑弹窗和浮动模式的新布局仍需细化，运行行为按实施验收核对。

| 模式 | OnO 采用的方式 |
| --- | --- |
| 并排 | 左侧 Bot，中间持续主对话，右侧原生工作区；工作区可独立收起，对话可展开为主区域 |
| 浮动 | 工作区优先，底部胶囊展开输入，当前答复浮在上方；可打开同一主对话的完整记录 |

### 3.1 外观适配规则

1. 顶栏沿用四组悬浮表面：紧凑 Logo 与导航开关、日程待办、工具与头像、系统窗口按钮。左上不显示应用名称；保留原按钮、动态避让和拖动规则。
2. 左侧悬浮导航改为 Bot 联系人，头像、名字和职责标签共同识别负责人；在顶栏与固定左下设置之间的可用区域垂直居中。原工作台子目录进入所选 Bot 的工作区，不把旧导航树再复制进联系人列表。
3. 主区域移除独立 Bot 头像、名字、职责及操作条，对话与工作区的顶边对齐到全局顶栏下方，保留必要间距；回收的高度用于正文和消息。Bot 身份由左侧联系人承担，联系人行用于切换工作台，旁边独立的信息按钮用于打开 Bot 名片，两个点击目标不混用。
4. 「并排／浮动」切换和「任务」放进对话面板已有标题行；「资料」放进工作区已有标题行，指向业务文件和素材。浮动模式通过胶囊或输入区菜单切换模式、打开任务，不新增一条外部工具栏。聊天、编辑器及按需打开的任务详情各使用稳定工作区面板。
5. Bot 名片默认关闭，点击信息按钮后在联系人旁覆盖展开，显示名字、职责和提示词摘要；「编辑资料」打开可滚动的编辑弹窗，提供保存和取消。名片采用清晰遮挡底面，点击外部或按 Esc 关闭并恢复触发按钮焦点；查看信息不挤动面板、不切换 Bot 或调用模型。导航收起时保留可通过键盘到达的名片入口。
6. 强玻璃作用于导航及面板外壳，保留透色、细亮边和柔和投影；正文、输入及任务内容使用更实的阅读底面。普通消息、协作行、局部标题和任务字段以间距、分隔线及浅色状态区分，不重复叠加玻璃卡片。
7. 浮动答复覆盖正文时提高遮挡，避免底下文章透字；答复可单独收起，输入框可收回胶囊。只保留一个可编辑输入区，答复层不越过所属工作区或遮住固定设置与任务详情。
8. 导航样式、玻璃强度、主题与助手并排／浮动模式分别控制。经典／悬浮导航均可使用两种助手模式，切换外观不改变 Bot、业务对象、草稿、任务和执行上下文。

## 4 OnO 接入位置

| 现有位置 | 接入职责 |
| --- | --- |
| `src/nav.ts`、`shared/contracts.ts` | 领域清单、Bot 与工作区绑定、原生模块路由 |
| `shared/ai-scope.ts` | 旧 scope、主对话和业务焦点的稳定身份迁移 |
| `electron/ai-core.ts` | Pi 持久会话与任务执行边界 |
| `electron/ai-ipc.ts` | Host 通信、工具注册、上下文及状态订阅 |
| `electron/ai-store.ts` | 扩展 OnO 自有 `chats.db`，保存档案、任务、逻辑收发箱、例行计划与触发记录、记忆及显示偏好 |
| `electron/main.ts` 与应用生命周期 | 首期托盘常驻、主窗口关闭与明确退出区分、Host 状态及单实例执行；后续接入独立 Host |
| `modules/*/ai.ts` 等实际贡献 | 业务工具、资源引用解析、确认和结果回执 |
| 原生模块存储 | 保持稿件、书目、命例、项目和待办原权威来源 |
| 系统凭据配置 | 沿用现有加密方式，密钥由宿主读取，不进入记忆或名片 |

当前执行仍采用临时 Pi 内存会话及最近聊天重放，接入时需要替换为稳定持久关联。通用工作台贡献本身不含业务工具，应逐个核对实际模块能力；例如稿件仍沿用现有修改建议与确认流程。

当前导航已把“日程待办”放在小工具的 `todo` 视图，`AiScope` 中待办仍关联 `home`。迁移时应统一导航、旧会话和快捷入口的领域绑定，不能只更换左侧标签。后续实施以当时的实际代码为准。

### 4.1 本地常驻与通信接入

采用通用方案第 7、8 节的持久消息、任务交接和事件唤醒；开源工程选型及官方源码入口统一维护在通用方案第 14.2 节。Pi 保持执行职责，OnO Host 负责寻址、收发记录、计划、通知和恢复。

第一阶段由 Electron 主进程持有 Host。收起助手、最小化或关闭主窗口后留在托盘，具备执行资源的任务继续；从托盘恢复同一 Bot、聊天和工作区。明确退出 OnO 时保存状态、记录中断并停止后台工作，下次启动按原任务核对恢复。

后续把 Host 拆成系统托管的独立本地进程，桌面 UI 通过本地 IPC 或 localhost 连接；UI 完全退出后仍可处理具备后台资源的任务。后台服务停止另设明确操作，自启与崩溃拉起监督实际 Host，并保证同一 OnO 数据实例只有一个有效执行者。

两阶段共用既有 OnO 数据根目录、身份和任务契约，界面显示 Host 连接及后台运行状态。等待确认保留待处理入口，恢复窗口不自动批准。电脑休眠或关机时停止推进，唤醒后核对收件箱、待回送结果和到期计划，避免重复执行或把所有错过的周期逐次补跑。依赖 OnO 窗口、浏览器及登录会话的能力需单独核对可用资源。

## 5 OnO 迁移要求

1. 备份 AI 自有存储，建立总 Bot 和领域 Bot 的稳定身份及主对话关联，迁移保持幂等。
2. 待办归待办 Bot，总 Bot 建立自己的主对话；旧的无 module 待办聊天保留来源，旧聊天、标题、对象和消息不拼接或改写 ID。
3. 待办共享数据和上游同步约束保留，不改写共享库中的非待办表；其他模块也保持原存储。
4. 设置从可接收新任务的领域中排除；旧设置聊天保留为历史。打开设置不新增模型调用。
5. 以持久 Pi 会话和任务替换逐轮临时执行；注册实际工具、资料读取和跨 Bot 消息，沿用业务确认。
6. 原生浏览器保留站点与标签约束，任务目标与页面选择分开；灵动岛及通知保留原来源、未读和定位规则。
7. 接入统一对话控制器后提供双模式，切换及收起不重发请求、不丢草稿、不停止已提交任务。
8. 接入托盘常驻、持久计划与触发记录，验证主窗口关闭后消息、调度和协作继续，明确退出后可核对恢复。
9. 按实际实现同步产品、视觉和行为规范，工作区中其他未完成修改单独处理。独立 Host 与系统托管作为后续阶段单独实施和验收。

## 6 未来接入 CMO 的映射

以下是基于 CMO 当前代码的接入建议，保存在本方案中作为复用检查，尚未改动 CMO。最终 Bot 划分、首页及待办迁移在 CMO 接入时确认。

| CMO 当前工作区 | 领域 Bot 建议 | 可保留的原生模块 |
| --- | --- | --- |
| 首页 | 总 Bot | 总台入口与跨领域概况；待办及日程按独立领域组织 |
| 权限管理 | 权限业务 Bot | 权限查询、群组创建 |
| 交付件管理 | 交付件 Bot | 项目交付件管理 |
| PBI 管理 | PBI Bot | 特性管理、子系统与模块 |
| DTS 管理 | DTS Bot | DTS 查询 |
| 设置 | 无 Bot | 人工设置、供应商、账号及接入配置 |

已核对的接入基础包括 `src/nav.ts`、`shared/ai-scope.ts`、`electron/ai-core.ts`、`electron/ai-ipc.ts`、`electron/ai-store.ts` 和实际模块贡献。CMO 同样使用 Pi、Electron IPC 和自有聊天库，可采用通用协议及界面控制器，业务规则由 CMO 保持。

CMO 接入需要特别保留：

- 权限 Bot 的名字表示权限管理业务职责，实际工具权限仍由 Host 和业务系统控制。
- PIC 群组、浏览器站点、W3 登录、WeLink 等能力逐项登记；群组提交已有内部确认，避免再叠加一次通用确认。“申请已提交”与“审批已生效”分别表达，结果不明时先核对。
- 普通工作台提示本身没有业务数据和专用工具；PBI、DTS、交付件等能力逐项接入，不因新增 Bot 档案就宣称已读写业务。
- CMO 当前 CodeAI 的 reply／failed 通知作为外部 Agent 事件接入，不直接等同于内部 Bot 协作或业务任务成功。
- CMO 独立管理自身名录、模型、凭据和 AI 数据。共享上游业务库仍服从原同步及归属规则，不自动与 OnO 合并聊天或记忆。

复用时替换领域名单、上下文提供器、工具、存储接入、路由及主题。共用的身份、会话、消息、任务、记忆规则和双模式状态保持一致。

## 7 实施与验收

按通用方案先验证 OnO 的身份和持久执行，再接入协作与恢复、托盘常驻、Bot 导航及双模式；随后实施独立 Host 阶段，总台完整首页单独重构。CMO 接入验证完成后再提取稳定共用包，维护同一份核心契约。CMO 按相同生命周期接入自身 Host，保持产品数据和凭据隔离。

除通用验收外，OnO 还需覆盖：

1. 总 Bot、待办及原快捷入口正确定位，旧聊天和共享业务数据可恢复。
2. 小墨整理稿件后与小历协作，结果回到原请求；“已接收”与“已完成”准确区分。
3. 外观组合、窄窗、浮动答复、并排展开、模式记忆及恢复一致，原生编辑操作可用；导航、材质、主题与助手模式可独立切换，面板内部不重复叠加玻璃卡片，覆盖答复不透出底层文字。主区域不再单列 Bot 身份行；名片可通过鼠标与键盘打开、关闭，不触发工作台切换或挤动布局。
4. 生成、等待协作、等待确认和失败时切换模式，草稿、对象、回复目标和后台状态不丢失。
5. 设置、实际写入确认、站点授权、灵动岛和通知原约束有效。
6. 托盘阶段关闭主窗口后，具备执行资源的跨 Bot 协作与定时任务继续；恢复窗口可定位结果，明确退出后停止后台工作。
7. 重启及休眠唤醒核对原消息、触发和业务回执，结果回原任务且不重复提交；空闲扫描不无条件调用模型。
8. 独立 Host 阶段验证 UI 完全退出、系统自启、实际进程异常拉起及单实例执行；首轮托盘验收不替代此项。
9. 使用真实模型和实际业务工具完成对应实施阶段的端到端验收后，再声明该阶段改造完成。
