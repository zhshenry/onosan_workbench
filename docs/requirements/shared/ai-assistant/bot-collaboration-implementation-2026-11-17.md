## 1 用户可以看到的变化

1. 在总 Bot 发起委派后，领域 Bot 的问题、修改确认和执行回执直接显示在发起对话。回答、批准、重试或取消使用原执行记录，不建立另一份可批准副本。
2. “还是20号吧”等明确补充可关联同一项未结束的工作。接纳补充时先冻结旧建议，再更新同一确认卡；旧卡、重复点击或迟到模型输出不能再次写入。多项候选在输入区选择；也可点击卡片旁“补充此项”，或明确选择“作为新工作发送”。
3. 点击紧凑交接行，在原对话区域查看两位 Bot 的持续往来，定位到原消息并可翻阅前后记录。查看范围不按工作切断，不增加第三列，不触发工作详情占用工作区的阅读布局。返回保留草稿、阅读位置和入口焦点。
4. 浮动模式显示补充所属的原工作与协作入口。双方记录仍使用原浮动表面，工作区位置和尺寸不变。
5. Bot 可发起只读询问或通知，正式委派仍有工作依赖和真实回执。通知不会自动触发互答；只读询问不获得修改、审批或读取用户私人对话的工具。内部询问执行记录不作为“已完成工作”通知用户。
6. 发送回执丢失后，以原发送 ID 核对。主窗口与灵动岛仍各自保存未发送输入；已发送消息、确认和结果同步。文字流合并保存并按记录传输，不再每个流式回调写入并广播整份历史。

头像绘制、角色动效、侧栏悬停外框及既有几何没有在本轮调整。

## 3 已固定的执行边界

新工作仍按 Bot 串行执行，等待确认/协作释放执行名额。补充只有明确属于未结束的目标时才更新原工作，多个候选先选择。`replyToTaskId` 的旧引用语义仍兼容；本轮新增的 `target.intent=amend` 才是明确修改当前工作的协议。

接纳补充后递增 `requirementsRevision`，下一次执行递增 `runGeneration`。旧运行的正文、工具预览和确认资格均按这两个值隔离。当前实现于模型请求/工具边界停止旧运行并从原持久会话继续；不会中途撤销已经开始的业务写入。浏览器实际步骤、正在写入、结果待核对和已结束任务仍拒绝不合适的补充，需要依据真实结果继续。

Bot 间消息可无业务根工作。只读询问为调度创建内部运行记录，使用独立执行历史，不插入接收 Bot 与用户的私人主对话；消息本身不因此被伪装成业务工作。通知落盘等待接收方正常下一轮读取，不自动发起回复循环。正式委派维持已有父子依赖。

模型名录只公开身份、头像、职责、能力和活动状态，不公开私人 instructions、记忆、凭据或主对话内容。接收方只获得本次明确传递的内容与授权引用，双方历史不会整段自动灌入模型。

## 4 可靠性与数据兼容

- 实施起点为前置界面聊天完成后的协议 v6、数据库 schema 4；当前为 `bot-workbench/v7`、SQLite `user_version=6`。
- 旧 Bot、主对话、任务、草稿、记忆和对象 ID 沿用；迁移前保留已有备份机制。新接纳和消息去重记录与任务更新在同一事务内提交。
- `bot-outbox.json` 由主进程持有，先持久记录发送快照再投递。相同 ID、不同内容/目的地/用途拒绝复用。较新的本地输入保存后才清理已确认的 outbox。
- 回执已存在时，重启后返回原结果，不重新建立任务。当前 Host 数据身份随新实例变化：旧请求没有可确认回执时，保守停止自动重发，以避免旧备份恢复造成重复写入。保留输入；完整的人工结束核对/恢复向导仍待后续补齐。
- 流式文字以约80ms为一批写入、广播。终止及重要状态立即 flush；异常退出可能丢失尚未落盘的一小批文字，业务确认/实际写入不依赖这批临时文字。
- 每个聊天维护独立序号并携带Host数据代际，旧代际事件丢弃；后台身份变化重取快照，不因不可恢复序号空转。最近256条记录事件用于补齐；遇到重置事件或过旧游标读取完整快照。大消息按256KiB块传输，单逻辑消息上限64MiB，超限明确拒绝，不静默截断。
- 新主进程只在旧 Host 空闲时接替；旧 Host 仍有执行/排队任务时保留保护，不强杀。开发窗口需要完整重启 `npm run dev` 才能换入主进程和 Host 代码。

## 6 合成性能测量与缓存决定

脚本：`tooling/bot-communication-benchmark.ts`。Node v24.16.0，30轮，100条历史、1000次文字回调；逻辑回调间隔4ms，80ms合并。旧基线复现完整聊天保存和序列化路径；新路径保存并传输变化记录。

| 指标 | 旧路径 | 新路径 |
| --- | ---: | ---: |
| 每轮保存次数 | 1000 | 50 |
| 每轮序列化传输字节 | 135,282,500 | 89,093 |
| 本地处理 p50 | 1183.61ms | 28.63ms |
| 本地处理 p95 | 1333.78ms | 33.19ms |

该合成样本写入次数减少95%，序列化字节减少约99.93%。这是固定样本的本地成本，不是实际模型延迟、用户悬停延迟或端到端回复提速倍数。

另测30轮新会话和30轮从持久会话重建：准备 p50/p95 分别为20.53/32.81ms、7.58/9.67ms。60轮本地模型夹具的 prompt 至首字 p50/p95为4.51/6.98ms；无真实网络模型参考意义。

目前持久历史重建成本较低，尚无 idle-cache 对照、内存常驻和长期泄漏证据，因此保持每轮释放 AgentSession。后续只有测得明确本地准备收益，且绑定失效/权限/对象隔离验证通过后再启用有限缓存。

## 8 2026-11-18 协作回传顺序与旧后台修复

用户报告：同一工作收到协作回复后，正文、思考和工具继续覆盖原条目；重启窗口后交接标记又移到正文前。另有一次工具失败被汇总为“1 项未完成”。

### 8.1 核对结论

- 对应新增待办的真实确认操作已经应用，随后只读核对也完成；失败的是一次向已结束子任务追加修正的工具调用，不能据此把整个工作标成未完成。未重放或修改这条真实业务记录。
- 当时实际连接的 Host 自 11 月 17 日 21:48 运行，早于回复分段代码更新，却仍报告相同 v7 契约。重启窗口没有替换这个后台；该任务三轮运行复用了同一 assistant entry。旧版覆盖过的中间正文不能凭空恢复。
- 通用完成回执只带操作数量，总管没有收到实际日期；本例又从旧交接指令推断写入结果，导致不必要的纠正交接。

### 8.2 已完成的修复

1. 契约升级为 `bot-workbench/v8`。Gateway 连接空闲 v7 Host 时先正常关闭旧后台，再启动当前构建；有运行／排队工作时沿用既有保护，不强制终止。数据库版本仍为 6。开发模式主进程不热更新，完整退出并重启后才启用此切换。
2. 每轮执行创建独立 assistant entry。遇到旧的 streaming 条目，冻结其已有正文、思考和工具，记录仍在执行的工具为中断；新回复不会继续写入旧条目。
3. Host 投递结果时持久保存 `pendingReplyMessageIds`；Runtime 在同一事务里将其转换为新回复的 `receivedBotMessages` 并消费，界面在该回复前显示可点击的“消息来自”。身份和消息定位随快照／增量一起保存，不需要为每个新接收标记再请求详情。
4. 发出事件留在原回复之后；领域确认卡留在对应交接段。旧版未分段记录按已知事件展示，不再按任务是否完成临时调整事件位置，不伪造已经被覆盖的早期回复。
