## 一、产品目标

每个 Bot 有一个主要工作区、一条持续主对话和一组获准使用的工具。用户能直接在工作区操作，也能把工作交给 Bot。接手的一方可以定位原对象、读到它的最新状态，知道目标中哪一步已经做完。需要其他专业能力时，当前 Bot 可以把明确的工作和资源引用交给另一位 Bot。

| 组成 | 产品约定 |
| --- | --- |
| 本地工作区 | 有稳定 ID，绑定业务对象、可用面板、工具和 Skill。“乐高区”、浏览器、终端、文件按实际能力并列开放。用户写的应用长期保存在所属实例里，原生业务数据继续由所属模块保存。 |
| 总管与领域 Bot | 默认负责人是总管，已有名字和身份沿用。用户也可以直接找领域 Bot。总管能操作自己的总台，跨域工作交给有能力的负责人，并从业务回执汇总结果。 |
| 预制与自定义 | 两者共用工作区实例和执行机制。预制模板由各产品随附，自定义实例由用户选面板、绑定资源、选择工具及 Skill。同一模板可以产生两个范围独立的实例。 |
| 工具与 Skill | 工具执行可验证的动作，Skill 说明如何组合动作完成工作。Host 和业务适配器在执行时核对工作区、原用户授权、对象及本次用途。名录根据实际绑定展示能力。 |
| 运行与互通 | 每个产品内由现有本地 Host 管理 Bot。询问、通知、委派、人工确认和真实结果沿用已有协议。窗口不可用时，依赖该窗口的操作等待资源。电脑恢复后先核对任务和在途写入。 |

首期按**各产品内 Bot 互通**设计。两仓共享行为约定、测试输入和已有事项库规则。聊天、办公资料、模型配置、凭据、浏览器登录范围和卡片目录分别由所属产品管理。既有跨应用共享待办以[事项库约定](../../../../../modules/todo/SYNC.md)为准。

## 二、GUI 和 LUI 共用什么

一次业务操作的路径是 **定位对象 → 读取当前状态 → 校验和执行 → 取得结果 → 更新工作区与对话**。GUI 提交用户明确保存的操作，LUI 提交解释后的同一种操作。各模块复用现有服务、校验和确认入口。先用总管看板和办公事项转待办验证下列行为，再从已运行的模块提取共用契约。

| 环节 | 两仓共同规则 |
| --- | --- |
| 指向 | 发送时固定工作区、目标对象及当时版本。能唯一定位的“刚挪的那张”“这条事项”可直接使用，多个候选让用户选一次。切标签、切 Bot 或切账号后仍按原目标核验。 |
| 状态与进度 | 模块返回正式状态和相关的已提交变化。人工操作可以没有 Bot 任务。只有明确目标中的动作才推进任务步骤。聊天、选中态、未保存草稿和业务已提交各有含义。 |
| 执行 | 写入携带操作 ID、操作者和目标版本，沿用领域确认规则。重复投递同一操作返回原回执。版本变化先重读，目标已满足即可核实交付，有冲突则保留当前值供重新选择。 |
| 回执与接续 | 写入者返回本次实际影响的对象 ID、最终版本或真实业务凭据。任务记录关联该回执，GUI 按它刷新，Bot 下一轮按对象 ID 回读。跨库或外部提交中断时保留“待核对”，先查原对象或业务记录。 |
| 委派 | 发送方给出目标、允许共享的引用和完成条件，接收方在自己的工作区复核。用户可从发起会话处理同一张确认卡。“已接收”“等用户确认”“业务已完成”分别显示。 |

原生面板可让 GUI 和 LUI 调同一个业务服务。第三方网页靠同一授权会话、标签页和最新观察接手，已适配站点再增加表单字段和业务回执。文件靠授权目录、对象位置和文件版本。终端靠受限命令、进程状态与产物，开放自由 Shell 的前提是实际的进程、文件和网络隔离。

### 持续对话与操作卡片

主聊天显示用户每次发送的原文、Bot 的答复与产物、确实需要等待的业务进度，以及确认、登录、澄清和可处理的失败。长任务可显示一句“正在核对原待办”，成功以对象回执为准。操作回执、待办确认、待回答和站点授权沿用同一个紧凑卡片。标题和摘要说明对象与变化，右侧显示真实状态和当前操作。单项新增可直接确认，批量或有风险的操作保留必要的预览。固定窗口、悬浮窗和桌面入口复用同一消息 ID，待处理的工作仍可在“工作与对话”中定位或取消。

用户可以在对话里点开相应卡片，也可以从 Bot 名片的「工作与对话」查看整项工作。两个入口读取同一份执行记录。展开后可看到“依据你选中的客户回访”“旧建议已失效”等可核对的步骤摘要，以及实际工具名称、必要的脱敏输入、耗时、结果、错误和关联回执。资料访问沿用当前账号与工作区范围。排查依据来自执行记录和业务事实。Grok 的直接消息可以改变当前方向，Muse 的头像入口能查看活动，两者分别提供了交互参考。[Grok 对话与改向](https://docs.x.ai/grok-bot/chat-and-collaboration) · [Muse 活动入口](https://muse.ai/blog/how-we-designed-muse)

三种高保真采用同一情境。11 月 21 日周六，用户先要求把“客户回访”安排到下周五，再补充“改成周四下午三点”。有效建议为 **11 月 26 日周四 15:00**，界面处于等待用户确认的状态。

| 对话设计 | 用户怎样排查 | 取舍 |
| --- | --- | --- |
| 对话操作卡片 | 点开业务卡的标题，在原位置查看本次操作的预览和回执。确认后在同一张卡上显示结果。 | 适合核对单次操作。所有状态共用同一张卡的布局。 |
| [从 Bot 名片看工作记录 · 高保真](../design/chat-details-2026-11-21/chat-activity.png) | 点名片的活动入口，现有侧栏定位到当前工作。图中为主动展开后的状态，原位置的建议卡显示最新日期。落地时给更新过的原卡标出对应的补充消息。窄窗覆盖正文，返回时恢复阅读位置。 | 适合作为双仓默认。聊天安静，还能查多轮、跨 Bot 的同一项工作。找某条很早的回复时多一步定位。 |
| [从业务对象看记录 · 高保真](../design/chat-details-2026-11-21/chat-object.png) | 点对话中的“客户回访”打开工作区里的目标对象，在对象详情查本次结果与变更历史。纯问答或尚无对象时走现有“工作与对话”。 | 最方便核对“究竟改了哪一条”，需要业务模块提供稳定对象链接。 |

### 消息如何确定工作和意图

**界面提供线索，当前产品的本地 BotHost 负责裁决，Pi 负责解释需要语义理解的句子。** 总管是业务负责人，普通领域 Bot 的每条消息都由所在会话直接进入 Host。第一版可在已有提交、补充和调度路径内实现。[OnoSan 提交入口](../../../../../electron/bot-host.ts) · [CMO 任务存储](../../../../../../cmo_workbench/electron/bot-store.ts)

1. **先接收。** 界面立即回显。Host 按 `clientRequestId` 持久化原文、顺序、Bot、会话和发送当时的回复对象、待确认卡或选中业务对象。重连与多窗口重发沿用同一 ID。
2. **分别判断指向和意图。** 原消息或确认卡的任务引用最强，其次是发送时选中的对象，再次是当前会话唯一相关的前台工作。引用解决“说的是谁”；同一对象也可能是新工作。状态按钮、直接回复卡片等明确指令优先用确定性规则。自然语言有多种解释时，把本 Bot 有权操作的候选工作、对象摘要和当前状态交给一次只读 Pi 判断。返回补充、另办、查进度、暂停或切换、继续、取消、需澄清及对应的候选 ID；组合指令按顺序返回。Host 复核归属、版本和可执行状态后才调度。候选仍有两个或模型不可用时保留原消息，只问一次带对象名的问题。
3. **在正确的任务生效。** “改周四”“下午三点，备注留着”按发送顺序补到同一任务。“顺便查明天会议”另办；“先停这个，先查会议”暂停原工作并提升查会优先级；“做到哪了”只读进度；“稍后做”进入后台等待。已有委派沿原父子任务转发补充并去重。后台例行工作按自身状态继续。
4. **分清接收、执行和已写入。** 同一任务使用需求版本和运行代次拦截旧输出与下一次写入。尚未提交的旧建议失效，已发出的读取可到安全边界结束。已提交或结果未知的写入按原操作 ID 核对，返回真实对象 ID 后用原业务确认规则修改同一对象。判定中的相关旧写暂缓到提交前复核。收到补充与等待回执可以同时成立，关闭重开后仍能处理。记录消息到达、落库、停止旧流及首条新反馈的时间，分别检查交互延迟与业务正确性。

### 乐高区的源代码和运行方式

“乐高区”是每个已开通工作区里的独立应用页签。用户可以新建或导入自己的小应用，也可以直接说“做一个计时器”“把这个跟进台改成时间轴”。每个应用有稳定 ID、可查看和继续修改的普通源码、所属工作区、入口和私有数据。一份应用可以设为工作区首页。复制到其他工作区时复制源码，重新绑定那个实例的数据与能力。

| 首版建议支持 | 作者实际交付的文件 | 工作台怎样运行 |
| --- | --- | --- |
| 原生 Web 应用 | 单个 `index.html` 可含 CSS、JavaScript；也可用相对路径拆成 HTML、CSS、JS 模块、图片和 JSON 文件。DOM、Canvas、表单和自定义计算均可自由编写。 | 从应用自己的隔离来源直接加载。普通小应用只使用浏览器标准 API 即可工作，宿主替单文件补齐入口信息。 |
| React 应用 | 真实的 `.jsx`、`.tsx`、`.ts`、`.css` 与本地资源，允许自行写组件、状态逻辑和交互。 | 使用安装包内固定版本的 React 和编译器，构建完成后加载产物。预览和错误反馈在本机完成，安装版应在未安装 Node/npm 的 Windows 环境验收。 |
| 后续有独立运行时的程序 | 如需 Python、Node 后台、任意依赖安装和长期命令，另行接入有文件、进程和网络边界的运行环境。 | 功能成熟后按工作区单独开放，与乐高区中的前端应用通过受授权的接口协作。 |

Pi 只获得当前应用的源码读取、编辑、构建及预览结果工具。宿主管理工作区文件边界、安装包内构建器、独立渲染沙箱、应用版本和实际加载结果。应用访问业务时，由宿主依据发起实例、当前授权、对象及版本复核。生成页用专用窄接口调用动作，拥有独立存储和网络范围；宿主保管主窗口接口、浏览器登录态和凭据。两仓的 Pi 会话都关闭默认内置工具。OnoSan 有面向用户的项目 PowerShell 终端，CMO 有结构化 WeLink 命令。两端普通 Bot 当前均未开放通用 Bash 或 PowerShell。首版编译调用固定构建工具。[Pi 0.85.1 SDK](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/docs/sdk.md#tools) · [OnoSan 项目终端](../../../../../electron/game-terminal.ts) · [CMO 的 WeLink 工具](../../../../../../cmo_workbench/modules/welink/ai-tools.ts) · [Electron 渲染沙箱](https://www.electronjs.org/docs/latest/tutorial/sandbox)

源码与可运行版本、应用自己的数据、原生业务对象分别保存。新版本先在预览中验证实际加载与关键交互，失败时回到最近可运行版本。应用改版与回退均保留已保存的业务操作。用户说“加一列”触发 Pi 编辑源码；说“把刚选的第二条改周四”则读取发送时的选择、顺序和对象版本，走 GUI 共用的动作与回执。涉及第三方网页时使用已授权标签的真实观察。

独立编写的普通 HTML 应用可直接渲染。深度接手通过一套可选的工作区接口实现，应用提供当前对象、已保存状态、有序选择和可调用动作。界面按钮与 Bot 共用同一业务处理函数。导入的第三方 HTML 若只提供界面，就按可观察的界面操作，并在能力清单中标明实际覆盖范围。

## 四、双仓并行路线

### 总管看板的双仓实现

总台用本产品的本地数据库保存正式布局，首次打开导入旧布局。GUI 和总管共用卡片目录、放置和尺寸规则，以及布局版本。写入回执包含操作 ID、最终版本和实际变化的卡片。ONOSAN 验收 AI 额度圆环，CMO 验收日程待办对比图。

“刚挪的那张”使用消息受理时最近一次保存的移动目标。多张卡片时按卡名选择。还在编辑的拖动会提示先点「完成」。总管保存后，打开中的人工草稿可继续查看，提交旧版本时会提示冲突。对话中的看板回执卡与名片工作记录读取同一次操作。

## 五、第一阶段试点与验收细则

### 两仓共同准备

1. 各自记录工作树版本、隔离数据目录和初始测试结果。使用合成资料，保留一份旧看板及一个空看板样本、一组有明确来源的办公事项样本，并约定两连接交错写入的次序。日期用例固定在周一的本地测试时钟，断言“本周五”和“本周四”对应的实际日期。
2. 各自在本仓从预制名单和真实页面登记业务动作。OnoSan 覆盖总台、日程、自媒体、游戏、网页、AI 测试、命理和阅读。CMO 覆盖总台、日程、办公、权限、交付件、PBI 和 DTS。盘点与试点开发同期进行。
3. 每项记录“工作区、用户动作、GUI 入口、Bot 入口、执行模块与对象 ID、授权或人工环节、成功凭据、尚缺环节”。现有服务可复用、缺工具入口、缺权威状态、需要人接管要能分别辨认。CMO 的交付件及 DTS 按已接入的数据源登记。
4. 两仓先把普通发送接到可去重的原对话消息与判定流程，再在同一交付批次撤下“引导／排队”控件。自动改向优先于视觉切换。对话操作卡与名片两个入口都可查看工作记录。确认、站点授权和失败留在原对话。

## 六、待做功能清单

**第一阶段从 1.1 到 1.3 开始。** CMO 依次接通来源、建议和实际待办。ONOSAN 同期推进 1.4 的动作盘点与 1.5 的安装版验收。两仓使用各自的本地事项库完成验收。

### 第一阶段 · 补齐办公接手和双仓联合验收

- [ ] **1.1 · CMO 发送时绑定办公事项。** 从「待处理」把选中的事项 ID、来源 ID 和账号范围传进普通对话，执行时复核。验收用两条同名事项，发完立刻切选，建议仍指向原选中的一条。切换账号后原引用应失效。
- [ ] **1.2 · CMO 的按钮和对话共用待办建议。** 补充办公助理的受限建议工具，复用准备、去重和确认逻辑。验收用“点按钮生成 → 对话改周五 15:00 → 用新卡确认”。全过程只有一张有效建议，确认前业务库零写入。
- [ ] **1.3 · CMO 按实际待办 ID 继续工作。** 确认时保存办公来源与写入返回的待办 ID，继承已有改期权限和确认规则。验收用“用户在日程里改到周四 → 助理读回周四 → 仍能打开原来源”。重复确认始终只产生一条待办。
- [ ] **1.4 · ONOSAN 与 CMO 并行完成预制动作盘点。** 每个现有工作区登记业务动作、GUI 入口、Bot 工具、对象 ID、状态来源、确认规则、实际凭据和缺口。ONOSAN 覆盖 8 个，CMO 覆盖 7 个；逐项标明已接入、待接入和需人工完成的动作。
- [ ] **1.5 · 两仓分别验收本地事项库和安装版。** 各自用隔离数据核对写入回执、旧版本冲突及中断恢复。升级安装版时用旧看板和空看板验证迁移，再验收聊天回显与接手。记录实窗、模拟模型及业务联调的环境。

### 第二阶段 · 乐高区候选方案（待定）

- **2.1 · 增加独立「乐高区」页签和本地项目。** 与浏览器、终端并列，支持创建或导入应用、查看和继续修改源码、运行预览。保存应用 ID、归属工作区、入口和应用数据。验收时重启可打开同一应用。
- **2.2 · 让 Pi 写出并运行原生 Web 应用。** 为当前项目提供范围内的读文件、写文件、编辑和查看预览结果工具。支持单个 HTML 文件和多文件 HTML/CSS/JS/本地资源。用户提出一句要求，Pi 的代码可在乐高区运行并根据错误继续修改。
- **2.3 · 接通应用里的业务动作与人机接续。** 约定当前对象、有序选择、已保存状态和版本的接口，由宿主核对权限和回执。验收时用户在应用中选第二条，Bot 在同一对象上完成下一步。单独修改应用源码后，原选择、应用数据和工作区里的业务记录仍可定位。
- **2.4 · 保存可运行版本与隔离预览。** 每个应用独立存储，失败时保留最近可运行版本。验收用一次语法错误、一次恢复、两个同名应用及一次重启，确认源码版本和业务数据分别保存，应用按已绑定能力访问数据。
- **2.5 · 增加 React/TypeScript 随包构建。** 支持 JSX、TSX、TS、CSS 与本地资源，把构建错误和实际预览结果返回给 Pi。用没有系统 Node/npm 的 Windows 安装版验收。HTML 流程先通过后再接这条路径。
- **2.6 · 两端各交付一个贯通业务的样板。** ONOSAN 的“本周待办板”演示人工选中、Bot 改期和加筛选。CMO 的“客户跟进台”演示按来源转待办及修改布局。两端都核对真实对象 ID、授权和回执。

### 第三阶段 · 浏览器和预制工作区扩展

- [ ] **3.1 · 双仓接手当前网页状态。** 发送时固定已授权的账号范围、标签和目标。人改了筛选、页码或表单后，Bot 重新观察继续。标签关闭、账号变化或页面状态失效时，能说明等待原因并保留工作进度。
- [ ] **3.2 · ONOSAN 验收网页与自媒体工作区。** 从用户筛选好的页面续查，核对结果、页码与来源。自媒体做一次人工接管前后连续操作。文章发布等已有确认边界随具体动作校验。
- [ ] **3.3 · CMO 验收 PBI。** 先完成现有标签的只读查询用例，再按已验证的业务接口开放其他动作。
- [ ] **3.4 · 按动作清单补齐其他预制工作区。** ONOSAN 逐域处理待办、自媒体、游戏、网页和网站、AI 测试、命理、阅读的差额。CMO 逐域处理日程、办公、权限和 PBI。每个开放动作都能从界面和 Bot 找到相同对象、权限与结果。

- **PIC 纯人工表单接手。** 候选范围为读回人工起填字段，保留已正确内容，再按权限补齐、确认和提交。按实际业务凭据区分「已提交」和「审批生效」。

### 第四阶段 · 自定义 Bot、文件与终端候选方案（待定）

- **4.1 · 从固定预制名单扩展到工作区实例。** 为模板、Bot 和工作区分别保存稳定身份。迁移现有 Bot、已改名资料、聊天、任务和交付件。验收同一个模板能创建两个独立实例，两端各自的资源绑定和工具权限可核查。
- **4.2 · 创建、配置和使用自定义 Bot。** 用户从模板或空白选面板、连接、文件范围、工具和 Skill，可组合乐高区、浏览器与文件。验收可在名录发现、直接对话和由总管委派，重启后还能找到同一实例和结果。

- **4.4 · 验收资源边界和跨 Bot 交接。** 用两个范围不同的实例测试同名对象、共享引用、授权变化、权限拒绝、人工接管及跨 Bot 返回实际回执。两仓均通过后记录该阶段完成。
