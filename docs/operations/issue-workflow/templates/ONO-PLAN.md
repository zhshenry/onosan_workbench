## 目标、范围、非目标与实现

<解决什么；各 Issue 修改哪些模块/接口/业务字段；明确不改什么；依赖与逐项验收；兼容/迁移/风险。>

每轮先全量检查，再按同一功能、强依赖或适合共同验收分组，不把无关需求打大包。单 Issue 默认也是一组；每组默认一个实现 PR，保留每个 Issue 及其逐项验收。一次只开发一组，独立分析可并行。

执行顺序：独立高保真 → 主方案 Issue 中文反馈迭代 → 方案批准 → dot 云电脑产品实现/测试 → 完成后实现 PR 并补齐其 CI → 主方案 Issue 最终合入收尾批准 → 实际 main 验证 → 满足已批准条件后关闭。不依赖用户电脑，不自行换保存云环境。设计 Draft 仅可选辅助，高保真不依赖产品代码或先 merge。定时任务只唤醒dot；沿用唯一协调者与简短state，不把自研调度器、分布式fencing、core迁pin或自动审批解析器列为方案实施前置。

## UI 高保真（确无 UI 才写不适用及理由）

<在本节与主方案 Issue comment 集中实际嵌入本组同版本全部相关图；成员 Issue 保留/更新各自对应图并互链，复用原生 URL、不重复上传。不能用跨 Issue 链接、代码示例、文字、线框或文档链接代替审阅图片。>

记录每图：状态/页面、设计来源、PNG SHA256、原始上传 comment、原生附件 URL、视觉检查与可访问性。源码渲染加完整设计源 SHA 和 run/attempt；独立绘图不适用项写原因。图片只上传一次，正文/comment 复用 URL，不入 Git、不备份。

审阅前必须备图；缺图只报阻碍，不能用“准备说明”请求 UI 审阅。实质 UI 修改升版本并更新相关图；方案迭代不等于产品实施。旧专用 renderer YAML 已退役，保留脚本不能作为日常 dispatch 入口；不改变安全控制或先扩建预览工程。

正常产品组目标是两关：本次设计/方案批准、最终准确 head 合入收尾批准。不得把设计 Draft、测试和普通安全重试逐项变成额外审批；也不扩大历史批准。已有原始批准记录准确 ID/URL、完整原文、作者、时间、目标和自发排除，不以本表自填作为来源证明。只有当时唯一明确请求覆盖全组，才可一次批准整组；某个 Issue 的单独批准不延伸到其他成员。组成员或范围变化须重新核对方案批准，新增或实质变化重新请求批准。

| 保存（适用时） | <有界读回业务字段、id/保留元数据、重载与同版本重启> | <实际值与断言；不只数量/toast> | 未覆盖 |

结果使用通过/失败/跳过/未覆盖，分类不自行豁免共同检查。截图/报告一轮合计 ≤20 MB、CI artifact 3 天；设计图不代替实现图。附件失败分类、先查结果、确认可恢复后最多补试一次；无证据不归因登录或目录。单次豁免必须明确另批，不成为长期规则。
